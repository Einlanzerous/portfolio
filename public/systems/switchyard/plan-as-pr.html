Problem statement

1 resolved

Between 09:12 and 09:23 UTC on 4 Aug, tenant argosy-eu replayed a backlog at ~40k events/min against POST /v1/ingest. The shared consumer pool saturated; ingest p99 for the other 811 tenants rose from 180ms to 4.2s and 14k events were shed by the queue's overflow policy. Nobody was paged — the SLO is per-service, not per-tenant.

There is no admission control in the path. Rate limiting exists only at Traefik, per-IP, which a single tenant with one egress address defeats trivially. Capacity is the only lever we have, and it is the slowest one.

Fixing this is a backend change end to end: a limits table, a hot-path check, a new response contract, and a way to turn all of it off. The console work is one settings panel.

Both are true, but they fail differently. A per-tenant SLO pages a human 11 minutes into the incident; a quota rejects at the edge in 40µs and pages nobody. Approach

chosen of 3
Comment
  • Token bucket in Redis, keyed quota:{tenant}:{minute}, checked in the ingest handler before the payload is parsed. One INCR + EXPIRE pipelined; measured 40µs p99 against the existing redis instance.
  • Limits live in Postgres (tenant_quota), loaded into a 30s process-local cache. Postgres is the source of truth so the admin API and the console edit one thing; Redis holds only counters and is disposable.
  • Reject with 429 + Retry-After and a X-Quota-Remaining header on every response, so a well-behaved client self-throttles before it is rejected.
  • Shadow mode first. The enforcing path ships off. For two weeks we count what would have been rejected, per tenant, and only then flip enforcement per tenant.

Rejected: Traefik middleware (no tenant identity at that layer), and consumer-side fair scheduling (fixes latency distribution but still accepts unbounded work — SWY-425 keeps the idea alive).
